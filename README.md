# Sunday Open · Рабочее пространство

Рабочее пространство Project Office AITU Volunteers: план на 4 воскресенья, шаблон 5W1H, коммуникации, медиаплан, локации, риски, калькулятор.

Сайт: GitHub Pages, ветка `main`, папка `/ (root)`. Исправления подготовлены в `codex/reliable-saving`.

## Изолированная тестовая версия

Рабочий `main` остаётся на `e8dd9b0`. Тестовая сборка создаётся из `codex/reliable-saving` и размещается отдельно: [Sunday Open TEST](https://nalatka.github.io/sunday-open-test/), репозиторий [Nalatka/sunday-open-test](https://github.com/Nalatka/sunday-open-test). Настройки рабочего GitHub Pages для теста менять не нужно.

Тест использует [собственную таблицу](https://docs.google.com/spreadsheets/d/1SMOX1RNy7CipaqbvKmTLs-QYlSMZsgS0EIHH64pAsNs/edit), скопированную из резервного снимка от 21 октября 2026, и [отдельный Apps Script](https://script.google.com/u/0/home/projects/1XWdbT4QqPvW0Wf2yhqXN977yyHcDX-z04XdPSp8RNqhwIc5-pYZYpMwi/edit). Правки теста не переносятся в рабочую таблицу. Для тестового скрипта `SUNDAY_SPREADSHEET_ID` должен быть равен ID из `preview.json`; исходный `apps-script.gs` содержит рабочий ID, поэтому его нельзя запускать в тестовом проекте без замены ID.

`node scripts/build-preview.cjs` создаёт `.preview/` с другим адресом API, отдельным ключом черновиков и заметной пометкой «ТЕСТОВАЯ ВЕРСИЯ». Сборка отказывается использовать рабочий адрес API или ID рабочей таблицы и проверяет отсутствие рабочего API в готовом HTML. Исходный `index.html` при этом не меняется. В тестовом репозитории публикуется только содержимое `.preview/` из ветки `codex/reliable-saving`, а не исходный `index.html` этого репозитория.

До первого запуска нужно авторизовать тестовый Apps Script, выполнить `setupSundayOpen`, создать его отдельное веб-развёртывание и записать `/exec` в `preview.json`. Пустой адрес блокирует сборку. После настройки `node tests/live-preview.cjs` проверяет настоящий тестовый API: независимые строки, конкурентную запись одной строки и повтор старого запроса после более новой правки. Проверка создаёт две временные строки и удаляет их через API; записи журнала остаются.

Тестовая версия опубликована 21 октября 2026. Проверка настоящего API прошла: разные строки сохраняются независимо, из двух конкурентных записей одной строки принимается одна, повтор старого запроса не заменяет более новую правку. В двух вкладках опубликованного сайта подтверждены сохранение разных строк и явный конфликт с сохранением локального текста. Черновик закрытой вкладки виден в истории устройства. Исходные значения изменённых полей тестовой копии восстановлены через API.

21 октября 2026 также выполнен `tests/browser-offline.cjs` в отдельном Google Chrome с чистым профилем и настоящим тестовым Apps Script. Проверены полный офлайн, перезагрузка с подтверждением предупреждения браузера, возвращение сети, перезагрузка при недоступном API и конфликт с правкой другого человека. Во всех проверенных сценариях локальные правки сохранились; после обычного восстановления связи сервер подтвердил запись, а при конфликте сохранил версию другого человека и оставил свою в черновике. Временная строка удалена через API. [Машинный отчёт проверки](tests/results/browser-offline-2026-10-21.json).

При полном офлайне перезагрузка пока открывает `ERR_INTERNET_DISCONNECTED`: сам сайт не кэшируется для работы без сети. Черновик при этом остаётся на устройстве и восстанавливается при открытии сайта после возвращения сети. Удаление данных браузера и использование другого устройства этой проверкой не покрываются.

Повторный браузерный прогон: `node tests/browser-offline.cjs` при доступном пакете `playwright` и установленном Google Chrome. Сценарий жёстко ограничен тестовым сайтом и ID тестовой таблицы; результаты и снимки экрана записывает в `.preview-check/`. Для обычных модульных проверок Playwright не нужен.

Проверка двумя людьми или двумя вкладками:

1. Открыть тестовый сайт в двух вкладках и дождаться «Все правки сохранены» в обеих.
2. Изменить разные строки одной таблицы. После сохранения и обновления обе правки должны оставаться.
3. Для конфликта в одной вкладке отключить сеть через инструменты браузера, изменить строку, во второй изменить ту же строку и дождаться сохранения. Вернуть сеть первой вкладке и нажать повтор сохранения. Должно появиться сообщение о конфликте; локальный текст должен остаться, а сохранённая строка команды не должна замениться.
4. Пока первая вкладка без сети, внести правку и перезагрузить страницу. После включения сети открыть тестовый сайт снова: черновик должен восстановиться. Если браузер не может загрузить сам сайт без сети, включить сеть для загрузки страницы — черновик уже записан локально.
5. При конфликте скачать копию перед выбором версии команды. Убедиться, что своя правка также доступна в истории черновиков. Калькулятор должен оставаться локальным.

Тестовые данные можно менять через тестовый сайт. Изменять напрямую `Data` и `SundayHistory` не следует: это обходит проверку версий. Публичный тестовый API доступен другим посетителям так же, как исходное приложение; для проверки используйте вымышленные данные.

## Сохранение

- `workspace-sync.js` сразу записывает черновик и очередь отправки в localStorage. Каждая вкладка имеет собственную запись: вкладки не заменяют черновики друг друга. После перезагрузки черновик восстанавливается; оставшиеся черновики можно открыть через историю на странице.
- Общие строки имеют постоянный `_id` и номер версии. Разные строки сохраняются независимо. При изменении одной строки двумя людьми сервер отклоняет устаревшую запись, а сайт сохраняет локальный черновик и версию команды. Автоматического слияния разных полей одной строки нет.
- Перед загрузкой версии команды конфликтующие правки архивируются на устройстве. Кнопка «Скачать копию» экспортирует текущую очередь, данные и полученные версии команды.
- «Все правки сохранены» появляется только после корректного подтверждения сервера для всей очереди. HTTP-ошибка, некорректный JSON, тайм-аут и ответ с отказом не очищают очередь. При недоступном localStorage появляется предупреждение, отправка приостанавливается.
- Повтор запроса использует тот же `mutationId` и исходное содержимое. Серверный журнал распознаёт повтор после потерянного ответа, включая повтор после перезагрузки или последующих правок другого человека.
- Калькулятор и его настройки сохраняются локально, команде не отправляются. Очистка данных браузера удаляет локальные копии; для отдельной резервной копии есть скачивание.

## Google Apps Script

`apps-script.gs` подготовлен по предоставленному скрипту и фактической структуре таблицы `Sunday Open Data`:

- `SharedTabs` содержит старые таблицы в JSON. Миграция читает массив из второй или третьей колонки только для известных общих таблиц сайта.
- `Data` хранит строки: `table, id, version, json, deleted, updatedAt`.
- `SundayHistory` — новый журнал с ID операции, хешем, версией, значением до и после изменения. Исходный `History` имеет другую структуру и не изменяется.
- В журнал сначала записывается полная операция, затем обновляется `Data`. Если выполнение прервалось между ними, следующий запрос достраивает `Data` из журнала. Подтверждение отправляется после `SpreadsheetApp.flush()`.
- Чтение, проверка версии, запись и миграция выполняются под `LockService.getScriptLock()`; см. [документацию Google](https://developers.google.com/apps-script/reference/lock/lock-service).
- Старые запросы целой таблицы и старые пакеты `ops` отвергаются. Новый клиент умеет читать прежние данные, но не отправляет правки серверу без протокола 3.

### Порядок включения

1. Сохранить резервную копию Google Таблицы и старого Apps Script. На время перехода остановить редактирование сайта и сохранить ещё не отправленные правки из старых вкладок.
2. В существующем проекте Apps Script заменить код на полный `apps-script.gs`, включая `SUNDAY_SEED` в конце. Старые `doGet`/`doPost` удалить, чтобы обработчики не дублировались. ID рабочей таблицы уже указан в `SUNDAY_SPREADSHEET_ID`.
3. Сначала опубликовать `index.html` вместе с `workspace-sync.js` и обновить все старые вкладки сайта. До обновления сервера новый клиент хранит черновики и показывает, что общее сохранение ждёт обновления. Дождаться завершения публикации GitHub Pages перед переносом данных.
4. Вручную выполнить `setupSundayOpen`. Он переносит рабочие данные из `SharedTabs`, сохраняет исходные листы, отмечает удалённые исходные строки и заполняет отсутствующие таблицы начальными данными. Имеющиеся строки `Data` не заменяются. При прерывании функцию можно повторить; неподходящие заголовки или изменившийся источник вызывают отказ вместо перезаписи листа.
5. Обновить существующее развёртывание веб-приложения на новую версию, сохранив действующие права и URL. Убедиться, что GET `/exec` возвращает `protocol: 3`, `ok: true` и объекты строк в `data`. Публикация нового `/exec` требует также заменить `SYNC_URL` внутри HTML. [Инструкция Google](https://developers.google.com/apps-script/guides/web).
6. На тестовой копии проверить две вкладки: разные строки сохраняются обе; одна строка приводит к явному конфликту; офлайн-правка переживает перезагрузку; удалённая строка появляется в `SundayHistory`.

Доступ к самому веб-приложению остаётся как в исходном проекте; версии защищают от случайного затирания, но не заменяют авторизацию. Напрямую менять `Data` и `SundayHistory` нельзя: их согласованность обеспечивает скрипт. Исходный `SharedTabs` после перехода остаётся архивом и больше не обслуживает записи нового сайта.

## Проверки

Без установки зависимостей, Node.js:

```sh
node --test tests/sync.test.cjs tests/apps-script.test.cjs
```

Проверяются настоящий клиент и `apps-script.gs` с имитацией сервисов Google Sheets, включая миграцию, конфликты, потерю ответа, повторную отправку, прерывание записи после журнала, несколько вкладок и восстановление черновиков. Эти проверки не заменяют проверку прав доступа и задержек настоящего развёртывания.
