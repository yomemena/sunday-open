# Sunday Open · Рабочее пространство

Рабочее пространство Project Office AITU Volunteers: план на 4 воскресенья, шаблон 5W1H, коммуникации, медиаплан, локации, риски, калькулятор.

Сайт: [Sunday Open](https://yomemena.github.io/sunday-open/). Рабочая сборка GitHub Pages: ветка `main`, папка `/ (root)`. Исходный шаблон — `src/index.html`, модуль сохранений — `workspace-sync.js`. Команда `node scripts/build-preview.cjs --production` собирает публикуемый `index.html` и версионные скрипты в корень репозитория, требует протокол 4 и сохраняет отдельные версии скриптов для офлайн-копии. После изменения исходников пересоберите и закоммитьте результат вместе с ними. Без флага скрипт собирает только изолированный тест в `.preview/`.

## Рабочая версия: сохранение и одобрение

Все общие правки, добавления и удаления сначала поступают на одобрение в `SundayProposals` рабочей Google Таблицы. Свой текст автор видит локально, остальные получают одобренные данные. Модератор выбирает одну строку предложения и меню **Sunday Open → Одобрить выбранную правку** или **Отклонить выбранную правку**. При отклонении локальный текст сохраняется. При одобрении сервер снова проверяет версию строки и не заменяет более свежую правку.

Адрес рабочего Apps Script сохранён. Он требует протокол 4; старые запросы целой таблицы и протокол 3 отклоняются. Для работы сайта Google-вход не нужен. Сама рабочая таблица закрыта от общего доступа: прямое редактирование `Data`, `SundayHistory` и кода обходит модерацию. Список разрешённых модераторов хранится в приватном свойстве `SUNDAY_MODERATOR_EMAILS`, а для нового модератора нужен и персональный доступ редактора к таблице.

Один раз откройте сайт с интернетом и дождитесь загрузки данных. Офлайн-копия устанавливается в фоне: постоянной служебной полосы и кнопки сброса калькулятора в рабочем интерфейсе нет. Статус показывается для ожидающих и проблемных правок; кнопки повтора и скачивания копии появляются при проблеме сохранения. После подготовки офлайн-копии страница открывается при офлайн-перезагрузке, а правки отправляются на одобрение при возвращении связи, пока вкладка открыта. Обновление офлайн-копии ожидает закрытия всех вкладок сайта. Очистка данных браузера удаляет локальные черновики. Вкладки старой версии нужно обновить; ещё не отправленный текст из старой версии следует отдельно скопировать перед обновлением.

## Изолированная тестовая версия

Тестовая сборка с одобрением данных размещается отдельно: [Sunday Open TEST](https://nalatka.github.io/sunday-open-test/), репозиторий [Nalatka/sunday-open-test](https://github.com/Nalatka/sunday-open-test). Настройки рабочего GitHub Pages для теста менять не нужно.

Тест использует [собственную таблицу](https://docs.google.com/spreadsheets/d/1SMOX1RNy7CipaqbvKmTLs-QYlSMZsgS0EIHH64pAsNs/edit), скопированную из резервного снимка от 21 октября 2026, и [отдельный Apps Script](https://script.google.com/u/0/home/projects/1XWdbT4QqPvW0Wf2yhqXN977yyHcDX-z04XdPSp8RNqhwIc5-pYZYpMwi/edit). Правки теста не переносятся в рабочую таблицу. Для тестового скрипта `SUNDAY_SPREADSHEET_ID` должен быть равен ID из `preview.json`; исходный `apps-script.gs` содержит рабочий ID, поэтому его нельзя запускать в тестовом проекте без замены ID.

`node scripts/build-preview.cjs` создаёт `.preview/` с другим адресом API, отдельным ключом черновиков и заметной пометкой «ТЕСТОВАЯ ВЕРСИЯ». Сборка отказывается использовать рабочий адрес API или ID рабочей таблицы и проверяет отсутствие рабочего API в готовом HTML. Рабочий `index.html` при этом не меняется. В тестовом репозитории публикуется только содержимое `.preview/` из ветки `codex/data-approval`, а не рабочий `index.html` этого репозитория.

До первого запуска нужно авторизовать тестовый Apps Script, выполнить `setupSundayOpen`, создать его отдельное веб-развёртывание и записать `/exec` в `preview.json`. Пустой адрес блокирует сборку. После настройки `node tests/live-preview.cjs` проверяет настоящий тестовый API: независимые строки, конкурентную запись одной строки и повтор старого запроса после более новой правки. Проверка создаёт две временные строки и удаляет их через API; записи журнала остаются.

Тестовая версия опубликована 21 октября 2026. Проверка настоящего API прошла: разные строки сохраняются независимо, из двух конкурентных записей одной строки принимается одна, повтор старого запроса не заменяет более новую правку. В двух вкладках опубликованного сайта подтверждены сохранение разных строк и явный конфликт с сохранением локального текста. Черновик закрытой вкладки виден в истории устройства. Исходные значения изменённых полей тестовой копии восстановлены через API.

21 октября 2026 также выполнен `tests/browser-offline.cjs` в отдельном Google Chrome с чистым профилем и настоящим тестовым Apps Script. Проверены полный офлайн, перезагрузка с подтверждением предупреждения браузера, возвращение сети, перезагрузка при недоступном API и конфликт с правкой другого человека. Во всех проверенных сценариях локальные правки сохранились; после обычного восстановления связи сервер подтвердил запись, а при конфликте сохранил версию другого человека и оставил свою в черновике. Временная строка удалена через API. [Машинный отчёт проверки](tests/results/browser-offline-2026-10-21.json).

В тестовую сборку добавлено открытие без сети. Один раз откройте [тестовый сайт](https://nalatka.github.io/sunday-open-test/) с интернетом и дождитесь надписи «Доступ без интернета готов». После этого его можно перезагружать без сети, продолжать редактировать и автоматически отправлять очередь после возвращения связи, пока сайт открыт. Если вкладка была закрыта и браузер не восстановил её сеанс, оставшийся черновик можно открыть через «Историю черновиков на этом устройстве». Конфликтующие строки автоматически не перезаписываются.

Service Worker сохраняет только HTML и два скрипта тестового сайта. Шрифты, изображения и основной код интерфейса уже встроены в HTML. Ответы Apps Script и запросы записи не кэшируются; общие данные и черновики сохраняет прежний модуль синхронизации. Имена скриптов и кэша зависят от содержимого сборки. Новая версия ожидает закрытия всех вкладок тестового сайта, не перезагружая редакторы с черновиками. Удаление данных браузера также удаляет офлайн-копию и черновики.

Проверено 21 октября 2026 на опубликованной тестовой версии в Google Chrome: страница загрузилась после перезагрузки в полном офлайне, позволила снова изменить восстановленный черновик, затем автоматически отправила обе очередные правки при возвращении связи без перезагрузки и кнопки повтора. Недоступность API и конфликт с правкой другого человека также прошли проверку. Временная строка удалена через API. [Отчёт с офлайн-загрузкой](tests/results/browser-offline-shell-2026-10-21.json).

Повторный браузерный прогон: `node tests/browser-offline.cjs` при доступном пакете `playwright` и установленном Google Chrome. Сценарий жёстко ограничен тестовым сайтом и ID тестовой таблицы; результаты и снимки экрана записывает в `.preview-check/`. Для обычных модульных проверок Playwright не нужен.

Историческая проверка двумя людьми или двумя вкладками до включения модерации (в текущем тесте каждую публикацию дополнительно одобряет модератор):

1. Открыть тестовый сайт в двух вкладках и дождаться «Все правки сохранены» в обеих.
2. Изменить разные строки одной таблицы. После сохранения и обновления обе правки должны оставаться.
3. Для конфликта в одной вкладке отключить сеть через инструменты браузера, изменить строку, во второй изменить ту же строку и дождаться сохранения. Вернуть сеть первой вкладке и нажать повтор сохранения. Должно появиться сообщение о конфликте; локальный текст должен остаться, а сохранённая строка команды не должна замениться.
4. Пока первая вкладка без сети, внести правку и перезагрузить страницу. После включения сети открыть тестовый сайт снова: черновик должен восстановиться. Если браузер не может загрузить сам сайт без сети, включить сеть для загрузки страницы — черновик уже записан локально.
5. При конфликте скачать копию перед выбором версии команды. Убедиться, что своя правка также доступна в истории черновиков. Калькулятор должен оставаться локальным.

Тестовые данные можно менять через тестовый сайт. Изменять напрямую `Data` и `SundayHistory` не следует: это обходит проверку версий. Публичный тестовый API доступен другим посетителям так же, как исходное приложение; для проверки используйте вымышленные данные.

## Сохранение

### Устройство одобрения данных

Модерация дополняет сохранение с версиями строк. Публикуемые рабочая и тестовая сборки требуют протокол 4: обычный HTTP-запрос создаёт только предложение в `SundayProposals`. Общие `Data` и `SundayHistory` меняются только после решения модератора. Старый протокол записи 3 в этом режиме отклоняется сервером.

На сайте появляется «Ожидает одобрения · локальные правки сохранены». До решения свой текст виден автору локально и переживает перезагрузку; остальные получают только одобренную версию. При отказе черновик сохраняется. Чтобы отправить исправленный вариант, измените текст. При одобрении повторно проверяется версия строки: более свежие изменения команды вызывают конфликт. Добавление и удаление строк также требуют одобрения.

Модератор открывает закрытую тестовую Google Таблицу, лист `SundayProposals`, выбирает одну строку предложения и меню **Sunday Open → Одобрить выбранную правку** или **Отклонить выбранную правку**. Колонки `before` и `after` содержат значения до и после. Служебные колонки вручную менять не нужно. Решение фиксируется с временем и подтверждённым Google-адресом модератора. Неизвестный или недоступный Google-аккаунт получает отказ; адрес из браузерного запроса не используется для проверки.

Список модераторов хранится только в **Apps Script → Настройки проекта → Свойства скрипта → `SUNDAY_MODERATOR_EMAILS`**, в формате JSON-массива, например `["moderator@example.com"]`. Для добавления модератора дополните массив и предоставьте ему доступ редактора к закрытой таблице. Сам список не публикуется на сайте. Авторы предложений пока анонимны; журнал не выдаёт произвольное имя или адрес из запроса за проверенную личность автора.

Порядок включения на тесте: сохранить резервную копию скрипта, убедиться в правильном тестовом `SUNDAY_SPREADSHEET_ID`, настроить список модераторов, обновить единственное активное тестовое `/exec` на новый код, затем выполнить `setupSundayModeration` под разрешённым Google-аккаунтом. Он создаёт `SundayProposals` и включает протокол 4. Лишние старые развёртывания того же тестового проекта нужно архивировать, чтобы они не принимали записи старым кодом. Перезагрузка закрытой таблицы добавляет меню Sunday Open. Тестовый клиент до включения протокола 4 хранит черновики и не отправляет их серверу протокола 3.

Публичные предложения могут заполнять очередь; число ожидающих ограничено 1000. Модерация предотвращает публикацию посторонних правок, но не заменяет вход авторов и защиту от спама. Проверки модерации: `node --test tests/moderation.test.cjs`. Исторические проверки `live-preview.cjs` и `browser-offline.cjs` рассчитаны на прежний тест без одобрения; в режиме модерации подтверждение записи требует решения в закрытой таблице.

21 октября 2026 на опубликованном тесте выполнен `node tests/browser-moderation.cjs` в отдельном Chrome с чистым профилем. Настоящий модератор через меню закрытой таблицы одобрил добавление, отклонил правку, затем одобрил исправление после офлайн-перезагрузки и удаление временной строки. Подмена признака одобрения в HTTP-запросе и старый протокол не опубликовали данные. Отклонённый текст сохранился у автора; офлайн-правка восстановилась после перезагрузки, отправилась при возвращении сети и стала общей только после решения модератора. [Машинный отчёт](tests/results/browser-moderation-2026-10-21.json). Повторный прогон требует ручных решений модератора для указанных в выводе `mutationId`; временная строка и история решений создаются только в тестовой таблице.

- `workspace-sync.js` сразу записывает черновик и очередь отправки в localStorage. Каждая вкладка имеет собственную запись: вкладки не заменяют черновики друг друга. После перезагрузки черновик восстанавливается; оставшиеся черновики можно открыть через историю на странице.
- Общие строки имеют постоянный `_id` и номер версии. Разные строки сохраняются независимо. При изменении одной строки двумя людьми сервер отклоняет устаревшую запись, а сайт сохраняет локальный черновик и версию команды. Автоматического слияния разных полей одной строки нет.
- Перед загрузкой версии команды конфликтующие правки архивируются на устройстве. Кнопка «Скачать копию» экспортирует текущую очередь, данные и полученные версии команды.
- «Все правки сохранены» появляется только после корректного подтверждения сервера для всей очереди. HTTP-ошибка, некорректный JSON, тайм-аут и ответ с отказом не очищают очередь. При недоступном localStorage появляется предупреждение, отправка приостанавливается.
- Повтор запроса использует тот же `mutationId` и исходное содержимое. Серверный журнал распознаёт повтор после потерянного ответа, включая повтор после перезагрузки или последующих правок другого человека.
- Калькулятор и его настройки сохраняются локально, команде не отправляются. Очистка данных браузера удаляет локальные копии; для отдельной резервной копии есть скачивание.

## Google Apps Script

`apps-script.gs` подготовлен по предоставленному скрипту и фактической структуре таблицы `Sunday Open Data`:

- `SharedTabs` содержит старые таблицы в JSON. Миграция читает массив из второй или третьей колонки только для известных общих таблиц сайта.
- `Data` хранит строки: `table, id, version, json, deleted, updatedAt`.
- `SundayHistory` — новый журнал с ID операции, хешем, версией, значением до и после изменения. Исходный `History` имеет другую структуру и не изменяется.
- В журнал сначала записывается полная операция, затем обновляется `Data`. Если выполнение прервалось между ними, следующий запрос достраивает `Data` из журнала. Подтверждение отправляется после `SpreadsheetApp.flush()`.
- Чтение, проверка версии, запись и миграция выполняются под `LockService.getScriptLock()`; см. [документацию Google](https://developers.google.com/apps-script/reference/lock/lock-service).
- Старые запросы целой таблицы и старые пакеты `ops` отвергаются. Новый клиент умеет читать прежние данные, но не отправляет правки серверу без протокола 3.

### Исторический порядок включения протокола 3 без модерации

Для текущей рабочей версии используется `setupSundayModeration` и сборка в корне с протоколом 4. Инструкция ниже сохранена для первоначальной миграции; не отключайте модерацию рабочего проекта.

1. Сохранить резервную копию Google Таблицы и старого Apps Script. На время перехода остановить редактирование сайта и сохранить ещё не отправленные правки из старых вкладок.
2. В существующем проекте Apps Script заменить код на полный `apps-script.gs`, включая `SUNDAY_SEED` в конце. Старые `doGet`/`doPost` удалить, чтобы обработчики не дублировались. ID рабочей таблицы уже указан в `SUNDAY_SPREADSHEET_ID`.
3. Сначала опубликовать `index.html` вместе с `workspace-sync.js` и обновить все старые вкладки сайта. До обновления сервера новый клиент хранит черновики и показывает, что общее сохранение ждёт обновления. Дождаться завершения публикации GitHub Pages перед переносом данных.
4. Вручную выполнить `setupSundayOpen`. Он переносит рабочие данные из `SharedTabs`, сохраняет исходные листы, отмечает удалённые исходные строки и заполняет отсутствующие таблицы начальными данными. Имеющиеся строки `Data` не заменяются. При прерывании функцию можно повторить; неподходящие заголовки или изменившийся источник вызывают отказ вместо перезаписи листа.
5. Обновить существующее развёртывание веб-приложения на новую версию, сохранив действующие права и URL. Убедиться, что GET `/exec` возвращает `protocol: 3`, `ok: true` и объекты строк в `data`. Публикация нового `/exec` требует также заменить `SYNC_URL` внутри HTML. [Инструкция Google](https://developers.google.com/apps-script/guides/web).
6. На тестовой копии проверить две вкладки: разные строки сохраняются обе; одна строка приводит к явному конфликту; офлайн-правка переживает перезагрузку; удалённая строка появляется в `SundayHistory`.

Доступ к самому веб-приложению остаётся как в исходном проекте; версии защищают от случайного затирания, но не заменяют авторизацию. Напрямую менять `Data` и `SundayHistory` нельзя: их согласованность обеспечивает скрипт. Исходный `SharedTabs` после перехода остаётся архивом и больше не обслуживает записи нового сайта.
